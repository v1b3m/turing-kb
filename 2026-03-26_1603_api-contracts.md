# Backend API Contracts For This Module Set

This document defines the finalized backend contract for the module set covered here:

- knowledge (articles)
- emails
- email-templates
- entitlements
- dashboards
- reports

The contract follows the existing backend patterns used by `cases` and `contacts`:

- Base path: `/api/v1`
- Auth: `Authorization: Bearer <token>`
- Standard wrapped response envelope for all JSON responses:

```json
{
  "success": true,
  "message": "Success",
  "statusCode": 200,
  "data": {}
}
```

- Standard paginated list payload inside `data`:

```json
{
  "items": [],
  "total": 0,
  "skip": 0,
  "limit": 20
}
```

- `204 No Content` responses return an empty body.
- Validation failures return `400` or `422`.
- Not found returns `404`.
- Uniqueness conflicts return `409`.

Important alignment decision:

- For `knowledge`, `emails`, and `email-templates`, field names intentionally mirror the current frontend record shape to minimize migration risk during the move away from `localStorage`.
- For `entitlements`, `dashboards`, and `reports`, the current frontend already uses mostly backend-style names, so those names are preserved.

## Shared Query Parameter Rules

List endpoints use the same baseline query parameters unless explicitly overridden:

- Required: none
- Optional:
  - `skip`: integer, minimum `0`, default `0`
  - `limit`: integer, minimum `1`, maximum `250`, default `20`
  - `q`: string, free-text search, default omitted

## Shared Date/Time Rules

- Timestamp fields stored as a full datetime string:
  - Format: `YYYY-MM-DD HH:mm:ss`
  - Example: `2026-03-19 09:00:00`
- ISO timestamps are allowed in create/update requests where noted, but responses must normalize to `YYYY-MM-DD HH:mm:ss` for UI consistency.
- Date-only fields:
  - Format: `YYYY-MM-DD`
  - Example: `2026-12-31`

`PUT /knowledge-articles/{article_id}`

- Same shape as create
- All fields optional
- `articleId`, `number`, `version`, `workflow` are server-controlled and must be ignored if sent

### Mandatory Fields

- Create:
  - `shortDescription`
  - `knowledgeBase`
  - `articleType`
  - `workflowState`
  - `introduction`
  - `articleBody`

### Optional Fields

- `category`
- `ownershipGroup`
- `sourceTask`
- `scheduledPublishDate`
- `validTo`
- `attachmentLink`
- `displayAttachments`
- `flagged`

### Null / Default Behavior

- `articleId`: generated by server, never null in response
- `number`: generated by server, never null in response
- `version`: defaults to `"1.0"` on create
- `active`: defaults to `true`
- `workflow`: derived from `workflowState`, always returned as a full array
- Optional text fields return empty string `""`, not `null`
- Optional boolean fields default to `false`
- `published` defaults to `""` until the article is published
- `scheduledPublishDate` defaults to `""`
- `validTo` defaults to `""` if not set
- `latestAQI` defaults to `""`

### Enum Fields

- `articleType`: `HTML | Wiki`
- `workflowState`: `Draft | Review | Scheduled for publish | Published | Pending retirement | Retired | Outdated`

### Field Format Constraints

- `articleId`: string, max 64 chars
- `number`: pattern `^KB[0-9]{7,8}$`
- `version`: pattern `^[0-9]+(\.[0-9]+)?$`
- `shortDescription`: string, min length `1`, max length `255`
- `introduction`: string, min length `1`, max length `1000`
- `articleBody`: string, min length `1`
- `updated`: datetime `YYYY-MM-DD HH:mm:ss`
- `published`, `scheduledPublishDate`, `validTo`: date `YYYY-MM-DD` or empty string

- `attachments` always returns an array, default `[]`

- `caseNumber`: pattern `^[A-Z]{2}[0-9]{7,}$`
- `sentAt`, `created`, `updated`: datetime `YYYY-MM-DD HH:mm:ss`
- `sysId`: UUID string if present
- `weight`: numeric string pattern `^[0-9]+$`

## Backend Validation Requirements Summary

The backend implementation must enforce the following for contract stability:

- Never omit array fields. Return `[]`.
- Never omit object fields that are part of the defined response schema. Return `{}` where applicable.
- For these modules, use empty string `""` for optional text fields unless the contract explicitly says `null`.
- Preserve exact field casing as defined above.
- Reject unknown enum values with `422`.
- Reject malformed dates and datetimes with `422`.
- Reject create payloads missing mandatory fields with `422`.
- Reject duplicate `email-templates` by `(table, name)` with `409`.

## Final Notes For Integration

- These contracts are intended to replace the current local persistence behavior, not coexist with it.
- The frontend can migrate module by module once these endpoints are available because each contract mirrors the current UI data shape.
- If backend prefers server-side field normalization later, that should be introduced only after the frontend no longer depends on the current record shape.
