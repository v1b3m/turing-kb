# Assets API Spec

Repo: `/Users/v1b3m/Dev/Turing/ServiceNow`  
Branch baseline: `amazon`  
Purpose: define the backend routes and frontend integration points needed to make assets fully e2e backend -> frontend.

## Goal

Support these features with real API-backed data:

1. View Installed Products
2. View Assets
3. Link Asset to Case

Current state:
- Installed products are already backed by entitlements.
- Assets are still local-only in `useAssetStore`.
- Cases can persist `asset`, but the asset picker reads from local store data.

## Scope Decision

Treat `Installed Products` and `Assets` as separate concerns:

- Installed products:
  backed by existing `/api/v1/entitlements`
- Assets:
  add a new `/api/v1/assets` resource
- Link asset to case:
  keep using existing `/api/v1/cases` create/update payloads, but source selectable assets from `/api/v1/assets`

## Proposed Backend Routes

### 1. List Assets

Route:
- `GET /api/v1/assets`

Query params:
- `skip: int = 0`
- `limit: int = 20`
- `q?: string`
- `asset_tag?: string`
- `display_name?: string`
- `model_category?: string`
- `assigned_to?: string`
- `company?: string`
- `state?: string`
- `substate?: string`
- `configuration_item?: string`
- `sort_by?: string`
- `sort_order?: "asc" | "desc"`

Behavior:
- Used by the main assets list page.
- Used by lookup dialogs where the case form needs an asset.
- `q` should search across at least:
  - `asset_tag`
  - `display_name`
  - `configuration_item`
  - `assigned_to`
  - `company`

Response:

```json
{
  "items": [
```

## Request/Response Schema Split

Use two response shapes:

### AssetListItem

For list and lookup use:

```json
{
  "sys_id": "asset-uuid-or-string",
  "asset_tag": "AT-001",
  "display_name": "Dell Latitude 5520",
  "model_category": "Laptop",
  "assigned_to": "John Doe",
  "company": "Acme Corp",
  "state": "In Use",
  "substate": "Deployed",
  "cost": "1299.00",
  "configuration_item": "LAPTOP-001",
  "updated": "2026-04-01 09:15:00"
}
```

### AssetResponse

For detail/create/update use:
- all `AssetListItem` fields
- all extended form fields currently held in `hardwareForm`
- nested JSON fields for:
  - `entitlements`
  - `contracts`
  - `device_entitlement_filter`
  - `device_entitlements`
  - `user_entitlement_filter`
  - `user_entitlements`

## Case Integration

No new case endpoint is required.

Existing case support is sufficient:
- `POST /api/v1/cases`
- `PUT /api/v1/cases/{case_id}`

Existing case payload already supports:

```json
{
  "asset": "AT-001"
}
```

Recommendation:
- keep storing `asset` as the selected asset tag or display value for now, to minimize churn
- if stronger referential integrity is needed later, migrate cases to also store `asset_sys_id`

## Recommendation

Implement this in two passes:

1. Pass 1
- add `/api/v1/assets` CRUD
- migrate assets list page
- migrate case asset lookup

2. Pass 2
- migrate full asset form
- clean up and remove `useAssetStore` local persistence from asset flows

This gives the fastest path to real e2e support for:
- viewing assets
- selecting an asset on a case
- persisting that case/asset link through the existing cases API
