In the 'Energy efficient home improvements' edit section, in the 'additional tax breaks' page multiple yes/no options questions were asked, for every question I selected 'Yes' as per the prompt, but those yes/no entries are not recorded in the localStorage.

---

## Resolution (2026-06-15)

**Root cause.** The energy efficient home improvements wizard (`app/index/tto/deductions/energy`) only persisted computed credit dollar amounts (`energyCredits`), `homeEnergyCreditCarryforward`, and `condoCoopEnergyShare`. The Yes/No gating answers (shared home, shared costs, home in U.S., clean energy, efficiency improvements + details, residential property + details, etc.) lived only in component state (`wizardDraft`) and were never written to `rm_tax_return`. Selecting "Yes" with the default $0 amounts produced no `energyCredits` entry either, so the answers left no trace in localStorage.

**Fix.** Added an `energyImprovementAnswers` object to the `Credits` type with a default + normalizer (so older records gain the field), persisted it through the existing `persistDraft` chokepoint on every selection, and restored it on wizard re-entry so editing the section shows prior answers instead of wiping them.

- Commit: `7501b83` — fix(energy): persist energy improvement yes/no answers to localStorage
- Files: `types/tax-return-types.ts`, `lib/energy-wizard.ts`, `lib/adoption-credits.ts`, `data/initializers/initialize-tax-return.ts`, `app/index/tto/deductions/energy/use-energy-credits-flow.ts`

**Verified live** (CDP, turing profile, localhost:3000): walking the wizard now writes `{sharedHome:true, sharedCosts:true, homeInUS:true, …}` into `rm_tax_return` on each Yes; re-entering the section restores the prior selections rather than nulling them. `pnpm typecheck` passes; eslint clean on changed files.

[R1] - 06/14/2026 - Suyash

The prompt asked the user to 'select yes for the question "Did Luma Labs LLC provide on-site child care?"' while editing the W-2 in the Your income and expenses page, but there is no state change reflected in the local Storage to evidence this change.

## Resolution (2026-06-15)

**Root cause.** Same pattern as the energy bug. The W-2 child-care step (`app/index/tto/income/w2/_step-child-care.tsx`) held its Yes/No answer in local `useState`. It only gated navigation (`goTo("savings")`) and was never written to `formData`, so it never reached `toW2Payload` / the persisted `W2Form` record. (The step is reached only when box 10 dependent care benefits > 0.)

**Fix.** Added `onSiteChildCare` to the `W2Form` record type and `W2FormData`, mapped it through `initialFormData` / `fromW2Form` / `toW2Payload`, and drove the step from `formData` via `updateField`.

- Commit: `d75da9d` — fix(w2): persist on-site child care answer to the W-2 record
- Verified live: editing the Luma Labs LLC W-2 and selecting "Yes" now writes `onSiteChildCare: true` onto that W-2 in `rm_tax_return`; before the fix the field was absent.
