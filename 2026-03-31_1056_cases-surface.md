## Executive Summary

The canonical `case` record is backend-backed. The frontend fetches, creates, updates, and deletes cases through `/api/v1/cases`, and the backend exposes full CRUD for cases.

The cases surface is mixed once you move into adjacent features:

- Case list/detail/create/edit: backend API
- Agent workspace case create/view: backend API for the case itself
- Case emails: backend API
- Agent tasks under a case: localStorage
- Knowledge feedback tasks / "knowledge gaps" under a case: localStorage
- Case list UI state: localStorage
- Draft attachments in the case/agent UI: in-memory Zustand only, not persisted and not backend-backed

## Bottom Line

If the question is "what is the system of record for cases?", the answer is the backend API and database via `/api/v1/cases`.

- Agent tasks
- Knowledge feedback tasks / case knowledge gaps
- Some attachment flows
- Case list UI preferences

## Backend-First Migration Plan

Goal: make the cases module itself backend-driven, with the frontend treating the backend as the system of record for case records and case-owned behavior.

### Principles

- No case-adjacent business data should live only in browser state or localStorage
- Frontend stores may still exist for transient UI state, but not as durable record storage
- Every list/detail/create/update/delete action visible in the case surface should map to a backend route and persisted model
- Mixed surfaces should be flattened so a case page is consistently sourced from backend queries

### Scope To Migrate

In scope:

- Canonical case CRUD
- Case-owned behavior and mutations
- Case-owned fields and relationships
- Case activity behavior where the case record itself is being changed
- Any case-specific derived views or counts that should be sourced from persisted case data

Out of scope for this note:

- Agent tasks
- Knowledge feedback tasks
- Other adjacent modules that may be linked from a case UI but are owned by separate domains

Separate modules should be handled in their own migration plans even if they appear inside the case workspace UI.

### Proposed Backend Surface

Existing canonical case routes remain:

- `GET /api/v1/cases`
- `GET /api/v1/cases/{case_id}`
- `POST /api/v1/cases`
- `PUT /api/v1/cases/{case_id}`
- `DELETE /api/v1/cases/{case_id}`

New routes likely needed:

Case-specific operations not well covered by the current CRUD shape:

- dedicated case action routes if we want explicit commands instead of broad `PUT`
- dedicated related-case management routes if we want to stop overloading full-record updates
- optional case workspace aggregation routes if the frontend needs a stable backend-owned projection

Optional aggregation route if needed for performance:

- `GET /api/v1/cases/{case_id}/workspace`

That route would return the case plus case-owned derived data needed for the case workspace header.

### Data Model Work

Cases:

- identify case mutations that should become explicit backend operations
- decide whether case activity should remain derived from case changes or become first-class persisted case activity rows
- ensure related-case links and other case-owned relationships are persisted through backend-owned writes

### Route Gap Recommendation

The current issue is not just missing routes. It is also that the case schema/model is narrower than the frontend case domain.

Recommended route strategy:

1. Keep generic case CRUD for ordinary field edits.

- `GET /api/v1/cases`
- `GET /api/v1/cases/{case_id}`
- `POST /api/v1/cases`
- `PUT /api/v1/cases/{case_id}`
- `DELETE /api/v1/cases/{case_id}`

2. Add explicit case action routes for case-domain commands.

Recommended first additions:

- `POST /api/v1/cases/{case_id}/close`
- `POST /api/v1/cases/{case_id}/transfer`
- `POST /api/v1/cases/{case_id}/clone`
- `POST /api/v1/cases/{case_id}/major-case/propose`
- `POST /api/v1/cases/{case_id}/major-case/accept`
- `POST /api/v1/cases/{case_id}/major-case/reject`

3. Add explicit relationship routes for case-to-case links.

- `PUT /api/v1/cases/{case_id}/parent`
- `POST /api/v1/cases/{case_id}/related-cases/{related_case_id}`
- `DELETE /api/v1/cases/{case_id}/related-cases/{related_case_id}`

4. If tags and attached knowledge are truly case-owned, add dedicated routes for them too.

- `PUT /api/v1/cases/{case_id}/tags`
- `PUT /api/v1/cases/{case_id}/attached-knowledge`

5. If activity is part of the case module, expose it as backend-owned data.

Two viable options:

- add activity fields into case responses after persisting them properly
- or add `GET /api/v1/cases/{case_id}/activity`

### Recommended Data Model Changes

Minimum backend expansion for true case parity:

- add major-case fields to backend case model/schema
- add related-case persistence beyond the simple parent string
- add tags to backend case model/schema if they are case-owned
- add attached-knowledge membership to backend case model/schema if it is case-owned
- add transfer metadata if transfer is a first-class case action
- decide whether case activity is embedded JSON or normalized child rows

### Recommended First Implementation Slice

Highest-value case-only slice:

1. Add backend support for major-case fields.
2. Add explicit major-case action routes.
3. Add backend support for related-case links.
4. Add explicit related-case link/unlink routes.

Why this slice first:

- these are clearly case-domain behaviors
- they are currently implemented mostly in frontend-only logic
- they create the largest mismatch between case UI semantics and backend ownership

### Deprioritize For This Note

These should not drive the cases plan:

- agent tasks

Those can remain separate migration tracks even if their counts or links appear on a case screen.
