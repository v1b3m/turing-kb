# Cases Capability Report

Date: 2026-04-01
Repo inspected: `/Users/v1b3m/Dev/Turing/ServiceNow`

## Summary

The backend exposes a solid `cases` API for CRUD plus a few workflows around major cases, relationships, tags, attachments, transfer, and close. Several other behaviors in the product are not backend capabilities and are currently implemented only in frontend state, especially case tasks and SLA timer displays.

## List 1

### 1. Associate a specific asset with a case

Status: Supported by backend API

Notes:
- The case model includes `asset`.
- The create and update schemas include `asset`.
- This can be done through `POST /api/v1/cases` or `PUT /api/v1/cases/{id}`.

Evidence:
- `backend/app/models/case.py`
- `backend/app/schemas/case.py`
- `backend/app/api/v1/endpoints/cases.py`

### 2. Use multiple criteria to find cases

Status: Partially supported by backend API

Notes:
- The list endpoint supports combining these filters:
  `q`, `ids`, `number`, `parent`, `state`, `state_not`, `major_case_state`, `major_case_state_not`, `exclude_id`, `exclude_number`, `parent_not`.
- These filters are all applied together in the backend query.
- The API does not currently support exact filters for `category`, `priority`, `assigned_to`, `assignment_group`, `asset`, or `account`.

Evidence:
- `backend/app/api/v1/endpoints/cases.py`
- `backend/app/services/case.py`
- `frontend/src/hooks/cases/caseApi.ts`

### 3. Group case list by category, priority, or assignee

Status: Not supported by backend API

Notes:
- There is no `group_by` or aggregate/grouped list route on `/api/v1/cases`.
- The cases API returns flat rows only.
- If grouping is shown in the UI, it would need to be done client-side after fetching rows.

Evidence:
- `backend/app/api/v1/endpoints/cases.py`

### 4. Toggle visibility of resolved/closed cases

Status: Partially supported by backend API

Notes:
- The API supports a single exclusion with `state_not`.
- Example: hide closed cases with `state_not=Closed`.
- The API does not support excluding multiple states in one request, so “hide resolved and closed” is not directly supported server-side.
- That exact behavior would need either client-side filtering or a backend enhancement such as `state_not_in`.

Evidence:
- `backend/app/api/v1/endpoints/cases.py`
- `backend/app/services/case.py`
- `frontend/src/hooks/cases/caseApi.ts`

## Overall Conclusion

### Clearly backend-supported today

- Associate a specific asset with a case
- Basic case CRUD
- Major case proposal/accept/reject workflows
- Parent-case association
- Generic case-to-case linking
- Case close
- Case transfer
- Tags, attachments, and attached knowledge updates

### Partially backend-supported or incomplete

- Multi-criteria find cases
- Toggle resolved/closed visibility
- View major cases affecting multiple customers
- See all cases for an account
- Customer portal creation/progress, only in the sense that the backend data/API exists

### Client-only today

- Case tasks under a case
- Marking case tasks complete
- Viewing all tasks for a case
- SLA timers and countdown on a case

## Frontend Usage Map

This section adds where the capabilities are currently consumed in the frontend so the work can be handled end-to-end from backend to UI.

- `frontend/src/hooks/cases/caseApi.ts`
  Thin client for the real backend cases endpoints:
  `fetchCases`, `fetchCaseById`, `createCase`, `updateCase`, `proposeMajorCaseApi`, `acceptMajorCaseApi`, `rejectMajorCaseApi`, `updateCaseParentApi`, `linkRelatedCaseApi`, `unlinkRelatedCaseApi`, `closeCaseApi`, `transferCaseApi`, `cloneCaseApi`.

  React Query wrapper around the cases API:

  Main case record UI where many of these features surface.

## End-to-End Impact

From an end-to-end backend-to-frontend perspective, the capabilities fall into three buckets:

### Already wired end-to-end through the real backend

- Case create/update/detail/list
- Asset on case
- Major case propose/accept/reject
- Parent case association
- Related-case linking
- Close case
- Transfer case
- Tags
- Attachments
- Attached knowledge

### Partially end-to-end, but with frontend-only filtering/interpretation layered on top

- Multi-criteria case discovery
- Hiding inactive/resolved/closed cases
- Major-case list views
- Case search by account text

### Not end-to-end yet because the frontend uses local-only state instead of backend resources

- Case tasks
- Task completion/state lifecycle
- Case task listing
- SLA rows, timers, countdowns

## Recommended Backend Gaps

If these capabilities need to be truly backend-supported, the smallest missing pieces are:

- Add exact case list filters for `account`, `asset`, `priority`, `assignment_group`, `assigned_to`, `category`
- Add multi-state exclusion support such as `state_not_in=Resolved,Closed`
- Add dedicated case-task backend model and CRUD endpoints
- Add dedicated case/task SLA backend entities and endpoints if timers must be authoritative
- Add explicit portal-facing routes only if customer portal access rules differ from the agent/internal case UI
