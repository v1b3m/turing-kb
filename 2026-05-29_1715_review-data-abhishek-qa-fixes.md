# Review: `data/abhishek-qa-fixes` → `origin/ots_dev`

**1 commit:** `cea594b` — "QA fixes: null/numeric coercion, ISO date normalization, generator hardening"
**92 files**, ~22.5K additions / ~21K deletions. Mostly data JSON, plus 7 Python files and 1 schema file.

---

## What the PR does

The PR fixes data quality issues in the Python data generation pipeline:

- **Null elimination:** All `null` values replaced with schema-safe empty values (`""` for text, `0.0` for REAL, `0` for INTEGER). A new `null_values.py` utility sanitises both top-level and nested JSON fields.
- **ISO date normalisation:** All dates converted to `YYYY-MM-DDTHH:MM:SS.000Z` at noon UTC (matching the `lib/civil-date.ts` convention). Both `YYYY-MM-DD` and `MM/DD/YYYY` formats are normalised.
- **Numeric coercion:** Expanded monetary field coverage in `numeric_types.py` — added `starting_balance`, `ending_balance`, `potential_deduction`, `rate_per_mile`, `qty_diff`, and nested JSON numeric keys. Non-zero integer-valued money gets `+0.01` to avoid JS `Number.isInteger()` confusion.
- **Generator improvements:** Customers get individual archetypes (`given_name`/`family_name`), terms get discount/day-of-month variants, items get more inventory coverage, bills get `paid_amount`/`paid_at` fields and AP account names, invoices/credit memos get `bill_email` from customer, report workflows get cadence fields, email logs get resolved customer emails, accounts/classes/departments get basic hierarchies.
- **Business logic:** New `_sync_bill_payment_status` and `_sync_accounts_receivable_balances` functions reconcile bill/invoice balances against payments.
- **Schema loader fix:** `UNIQUE(company_id,...)` without space before `(` now correctly skipped instead of leaking bogus columns.

## Issues found

### BLOCKER: `defaultState.json` not regenerated

> [!danger] Blocker
> `defaultState.json` has **2,367 nulls** and **1,614 date-only/US-format strings** that no longer match what the stores will produce when loading from the updated seed data. When `/state-diff` compares localStorage (from new seed) against defaultState (old format), it will report massive noise on every store.

| Gap | Count |
|-----|-------|
| Date-only `YYYY-MM-DD` values in defaultState | 1,115 |
| US format `MM/DD/YYYY` values | 353 |
| Midnight UTC `T00:00:00` values (should be noon) | 146 |
| Null values | 2,367 |
| Stores affected | 17 of 17 |

The `--sync-default-state` flag only coerces monetary fields — it does **not** rebuild defaultState from seed. `defaultState.json` must be rebuilt (load the app, clear localStorage, export) before merge.

### CONCERN: `paid_amount` / `paid_at` added to bills schema but ignored by store

> [!warning] Concern
> `updatedSchema.ts` adds two columns to the bills table (lines 62–63). The generator populates them. But `store/bill-store.ts:494-536` (`transformSeedBill`) **doesn't read them** — it derives `paidAmount = total - balance` and `paidAt = billDate` from existing fields. The seed fields are dead data.

Either the store should read from seed (preferred for consistency) or the schema columns and seed fields should be deferred until the store is ready to use them.

### CONCERN: `_rebuild_email_logs` still emits `None` for `cc_emails`

`seed_quality.py:330` — `"cc_emails": ... else None`. This is cleaned up by `_vary_email_log_delivery_fields` and `coerce_empty_values` downstream, so the output is correct. But it relies on downstream repair rather than emitting `""` directly.

### MINOR: Duplicate `filing-1099.json` / `filing_1099.json`

> [!note] Minor
> Two seed files for the same entity with different schemas.

- `filing-1099.json` (dash) — camelCase keys, 9 fields. **Used by `prepare-1099-store.ts`**.
- `filing_1099.json` (underscore) — snake_case keys, 11 fields. **Generated by pipeline**.

Pre-existing issue, but this PR modifies both. They should be reconciled.

### MINOR: `_populate_basic_hierarchies` cross-type parenting

`seed_quality.py:645-660` — parent accounts can be `{Expense, Income, Bank}` but children are `{Expense, Income}`. An Expense sub-account could end up under a Bank or Income parent. Not realistic accounting, though likely harmless for generated data.

### MINOR: `_sync_accounts_receivable_balances` sets `opening_balance = current_balance`

`seed_quality.py:270` — setting `opening_balance` to the current outstanding invoice total implies no change over the period. Acceptable for seed data but semantically incorrect.

### INFORMATIONAL: Report workflows generator still emits non-ISO dates

The generator at `table_generators.py:1711` still hard-codes `"05/16/2026"`. The normaliser catches it downstream, but the generator should emit ISO directly.
